# MIC-01 exploratory maintenance interface comparison

Authorization: user requested continuing the advantage investigation on an
existing Linux host, 7 November 2026. This is new work; it does not reopen,
replace or rescore P20–P38, RDR-01/02 or the paper's existing observations.

## Question and scope

On the SAME original ALVA maintenance tasks, does the current Native semantic
interface bundle produce more correct completed candidates, or lower observed
cost, than a controlled strong source-editing workbench? This tests an interface
bundle, not superiority of ALVA over Python or all mature coding agents.

Six known tasks: MM01/MM02 from P29 and MM04–MM07 qualified in P37. These are
historically selected, author-familiar tasks, NOT six new independent tasks.
Three component sources (demo, build, store); three tasks share build.model.
MM01/MM02 already have selected S-only successes; these are new independent
sessions, not a historical Text arm paired with those runs. No efficacy claim
may hide selection, model prior exposure or task correlation.

Task order and arms are registered before generation. Two repetitions per task
per arm = 24 slots. Counterbalance T/N order within each task across repetitions;
shuffle pair order with seed 20261107. Concurrency 1. No model slot replacement,
additional turns, prompt changes, witness hints, changed tests or reruns after
failure. Candidate-local failures continue; common infrastructure/isolation,
credential, unexpected tool exposure, reroute or unconfirmed cleanup faults
stop new launches. Such faults are retained and are not model failures.

## Conditions and resources

Use the historically used gpt-5.6-sol, low, if returned by actual model/list;
otherwise stop before generation rather than substitute. Pin CLI binary/version,
ALVA ELF, Rust toolchain, public Cargo registry, controller/service and all inputs.
New auth-only AppServer context and ephemeral session per slot; no repository,
research history, previous responses, evaluator implementation or witnesses
mounted in model workspace. No model-context inheritance or delegation.

Both arms get identical public task, original source, language documentation,
full official Skill/reference bytes, study read/search/diff/check/test/finish
feedback and scope rules. Instructions override the Skill's Native-first route
in T: it has no Native tools and uses its complete source editor. Native tools
and their schemas are visible only in N. No hand-written solution scaffolds.

T: revision-bound unique text replacement AND full-file replacement, ordinary
Git diff. Full-file replacement can express any permitted source body rewrite;
it is not restricted to the author's anticipated edit. N: actual twenty public
Native MCP tools, official Skill, public constructors and commits, no Core edits.
No shell in either arm. This is a controlled interface experiment; it is not a
comparison against unrestricted Codex/Claude source-editing products.

Each slot: 1 turn, 80 total model tool calls (Native + study), 480 seconds active
turn observation, 600,000 cumulative reported-token observation threshold,
20 seconds interrupt grace, no provider hard-cap claim. Same thresholds in both
arms; tool-call limits may favor coarse source edits over fine Native steps,
which must be reported rather than silently equalized. Maximum 24 slots.
Do not subtract cached input from reported total. Provider requests/costs null
unless reliably reported. Limits include check/test waiting. Report setup time
separately; raw total/cached/input/output/reasoning fields preserved.

## Equal outcome gate and independent evaluation

Both arms are disposable candidate workspaces, NOT production publication.
The unchanged P34 snapshot mechanism supplies complete baseline/final structural
evidence for scoring in both arms. No live P34 prevention in either arm, so an
extra preventive gate is not credited to N. Native commit is still required to
publish its AIR candidate for final evaluation; uncommitted staging gets no
completion credit. T source bytes are its candidate authority. Both face the
same final protected-body/metadata condition. No final state rescue or repair.

Public check and test feedback is identical: compiler diagnostics plus bounded
combined goal/regression pass/fail. Hidden assertions and expected values never
return to the model. Final evaluation is an independent fresh Linux namespace
over exact candidate source/AIR bytes, using the same pinned goal/regression
assertions. A fresh Native process re-reads each valid final authority. Record
the tested snapshot digest explicitly. Finite assertions are not a proof.

Baseline preflight must establish goal TEST_FAIL and regression PASS for all six.
Technical preflight uses no model turns. Synthetic transport/controller tests
do not consume or replace the 24-slot schedule. Unsupported tasks retain their
registered row; do not swap easier tasks in.

## Endpoints and interpretation fixed before generation

Primary: correct completion = terminal confirmed, independent task PASS,
regression PASS, target body changed, no unauthorized structural changes,
protected metadata unchanged, exact fresh authority binding, no invalid-tool
or infrastructure fault. Abstention/no-op/failure/time limit are not successes.

Secondary per slot: terminal reason, tool calls/errors, checks/test attempts,
active wall time, setup/finalization time, reported token categories, actual
Native commits and final unauthorized body edits. Report denominators and
incomplete usage, not zeros. Present all slots plus paired per-task results.
Only compare completion cost among pairs where BOTH succeed, with survivor
selection clearly stated; also report total experiment resource consumption.

Two repeats are not independent new tasks. No pooled significance claim or
success-rate generalization. Bootstrap or power/sample-size planning for a
later study must respect task/component clustering; no extra slots here.

Exploratory favorable signal only if N has more paired successes, or no fewer
successes plus >=20% lower median reported tokens in at least four complete
both-success paired observations. This is a prespecified screening threshold,
not proof of superiority or statistical significance. Otherwise report no
favorable signal; infrastructure-missing comparisons are inconclusive.
Do not select an unregistered favorable metric after observing results.

If signal exists, propose an independently reviewed fresh-task study. Do not
automatically start it. If parity/adverse outcomes, diagnose actual failure
categories; do not expand Core, tune prompts or rerun this pilot to manufacture
an advantage. The current paper remains a case study until new evidence is
separately reviewed. No paper claims updated automatically.
