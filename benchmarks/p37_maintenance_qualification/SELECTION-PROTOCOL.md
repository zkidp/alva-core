# P37 prospective selection protocol

Base: `6d5eab29e801415be1054e02ef6cf2335a3c091b`. Zero model generation and
zero input-token API calls. Codex-authored requirements, tests and witnesses
are engineering materials, not independent human ground truth or Agent results.

Register exactly four candidates, in MM04–MM07 order, before executing any new
engineering witness. No adaptive candidate replacement or additional wave to
fill a PASS quota. Preserve every registered result, including failure or
blocker. A concrete definition error requires additive correction/supersession,
retaining the original definition and its result. Historical MM01/MM02/MM03
dispositions and all P20–P36 artifacts remain closed and unchanged.

Source search: existing Apache-2.0 public example modules first, then valid
self-contained test projects; negative compiler fixtures are not maintenance
candidates. Prefer behavior changes requiring control/data flow over constants
or cosmetic renames. Do not create a new program, simplify an existing function,
change a signature to mimic MM03, or add platform capability. The four selected
requirements are plausible requested maintenance, not independently reported
production defects. They span graph/error completeness, state-dependent cache
invalidation, stable collection aggregation and XML text encoding. Three share
build.model and one uses store.model: this is two correlated component sources,
not four independent products or evidence of broad industrial coverage.

Component slicing retains the **entire exact original module**, including
non-exported functions/types/tests. Only an explicit new single-module manifest
is supplied. The full build-system/store application is not exercised. Source
bytes and Git origins, license blob, adaptation and complete trusted inventory
are registered. No source alpha-renaming, pre-unsharing or test removal.

Before witnesses: commit/push registry, original bundles, public tasks, approved
docs and trusted assertion source. The qualification driver must bind those
registered bytes to that commit. Task requirements, authorization and assertion
criteria cannot be changed in response to outcome. One batch executes all four
in that fixed order; per-candidate exceptions are retained and do not suppress
later candidates. Harness errors may be diagnosed without changing the task;
all executed attempts must remain in controlled evidence, not overwritten.

For each: baseline check/build plus regressions PASS and new goal TEST_FAIL;
Text witness in a separate isolated source-only copy with source and named-body
scope comparison; Native witness only through the actual twenty public tools,
with real P34 Guard, staged body roots/preview/check, underlying commit count,
fresh-process AIR revision/body roots and separate independent evaluation.
No public schema is treated as behavioral proof. A known missing Native tool
requires actual catalogue/refusal evidence; absence of a guessed sequence is
not a mathematical impossibility claim. Current Guard supports complete fixed
function-body scope, not signature/type/export/module evolution.

Disposition rules, registered before execution:

- QUALIFIED_MATCHED: both sides pass goal/regressions/scope, Native additionally
  has actual allowed commit, AIR publication and matching fresh authority.
- TEXT_ONLY_NATIVE_UNSUPPORTED / NATIVE_ONLY_TEXT_UNSUPPORTED: one side passes,
  the other has concrete interface/Guard support limitation.
- CANDIDATE_LOCAL_FAILURE: valid definition but attempted deterministic route
  fails behavior/check/scope; no unsupported-interface claim without evidence.
- INCONCLUSIVE_WITH_BLOCKER: specific infrastructure/evaluation failure.
- EXCLUDED_AT_REGISTRATION: fails an explicit registration criterion before
  any witness; retain it. No such exclusion is assumed in advance.

Tests exercise finite bounded values, not universal semantic equivalence.
Scope is changed declaration coverage, not all dynamic dependents. Engineering
qualification only makes a task eligible for a separately authorized future
freeze; it does not start or budget a model slot.

Future model inputs are constructed by an explicit allowlist from public task,
original bundle and approved docs only. Text receives language docs; Native
also receives full official Skill/references and actual schemas. Registry
capability hypotheses, trusted assertions, witness code, attachment revisions,
qualification diagnostics and other task history are never model inputs or
candidate mounts. No model runner is provided. No Text/Native advantage or
model success-rate claim, P38, automatic merge or historical rerun.
