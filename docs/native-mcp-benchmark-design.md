# Native MCP/Skill benchmark: minimal future design, NOT EXECUTED

Question: with individually advertised native ALVA MCP schemas and the full
native Skill, does Codex more reliably discover/call operations, stage a useful
change and commit than with P21's thin JSON bridge?

This is a proposed independent developmental study, not a rescue/continuation
of P21 and not a language correctness or superiority claim. No model results
or executable model schedule are produced in this node. Separate explicit
authorization and a complete immutable execution freeze are required.

## Smallest informative prospective wave

Reuse P21's four public adapted task **types**, bounded domains and independent
input/output evaluation ideas. Use new slot IDs, sessions and initial stub
copies. Supply no P21 candidate, patch, conversation, failure-specific recipe
or reference. Freeze the final task statements/vectors/stubs again before
generation rather than calling this document an execution-ready package.

Propose four tasks x three conditions x one run = at most twelve new tasks:

| Condition | Mutation/knowledge surface | Role |
|---|---|---|
| T | ALVA Text read/edit/check/build/test | Source coding comparison |
| B | Thin JSON Bridge to AEP, with its explicit limited bootstrap | Concurrent bridge baseline, not reused historical outcomes |
| N | Existing native MCP operation schemas + complete existing ALVA Skill and referenced docs | Native discovery/workflow package |

The primary interface comparison is **N vs B within this new wave**. T vs N
is separately an end-to-end model-use comparison. P21 may be historical context,
never pooled as fresh paired controls. Python is not necessary for this narrower
question. Native schemas/Skill are a real additional information/affordance
treatment; do not describe B and N as equal tooling or attribute any gain solely
to semantic correctness, transactions, or more compact representation.

## Required freeze, before any generation

- Exact task sources/licenses, adapted text/domains, stubs and typed independent
  vectors; no reference implementations in model-readable mounts.
- Source authority vs AIR authority rules, edit scope and final artifact extraction.
- Exact canonical MCP binary/server/plugin packaging and schema bytes, Skill text,
  all referenced documents and how/when each is delivered or expanded. Record their
  bytes/tokens; do not silently add task-specific examples or bootstrap names.
- Full controller/transport/input closure via v2 exact-byte transport, approved
  environment/runtime and platform-specific SDK identities. Actual runtime
  content must match before invocation, not merely belong to an accepted EOL set.
- One exact model/provider/reasoning configuration, resolved metadata and reroute
  policy. Prospective budget values and stop semantics must be frozen; if the
  host exposes only token observation, label it as such, not a hard cap.
- Fresh randomized/interleaved order, no retries/replacements, candidate-local
  failure vs common-infrastructure HOLD rules, and a disposition for missing
  usage/terminal confirmation. No automatic threshold/budget expansion.

The present v2 batch runner is **not** a validated native MCP stdio sandbox
adapter. Before this wave, add only the necessary trusted launcher/stream proxy
so the MCP/agent process consumes candidate source/AIR inside a persistent
namespace, and put every untrusted check/build/generated executable in the same
effective isolation boundary. Do not let a host-side test callback bypass it.
Validate real tools/list discovery and scoped Skill loading with no model first;
no need to reopen P0/P1/P2's historical acceptance. Native Windows is unsupported
until a real backend exists; use an explicitly frozen supported Linux environment
or refuse the wave, never fall back to ordinary host permissions.

## Outcomes, separated by stage

Per task/condition, capture:

1. Delivery/discovery: advertised operation count/schema identity, Skill delivery,
   successful schema fetch and entity resolution, guessed unknown names.
2. Calls: valid/malformed calls, missing required fields, stale handles, API errors;
   `ok:true` is not proof of a useful change.
3. Change: detached construction vs target-connected edits; useful staging,
   transaction checks, rejected/accepted commits, fresh authority reread.
4. Correctness: final compiler status and host-independent execution of the final
   committed artifact (or explicit NO_COMMITTED_CANDIDATE), plus same public checks.
5. Burden/stopping: provider-reported input/cached/output/total without subtracting
   cache, available provider-request counts (otherwise null), tools, check/build
   time, wall time, first target edit, repair attempts, acknowledged interruption
   and terminal confirmation. Unknown usage is not zero.

Analyze each task first. Increased schema/call correctness without a connected
edit/commit is a discovery signal only. More commits without behavioral PASS is
lifecycle closure only. More behavioral PASS with extra documentation is a
workflow-package observation, not proof of AEP's semantic superiority. Report
all failures and costs. No significance test or generalization claim is justified
by this tiny wave; repeatability would require a separately authorized study.

Independent ground truth must be outside candidate-readable reference material.
Use host-owned input/output comparison, including recursive value/type semantics
where relevant; do not silently carry P21's disclosed nested-type limitation.
Do not classify a never-committed default stub as a bad semantic commit. Keep
mechanical safety, operation completion and final task correctness distinct.

Decision remains for reviewer/user. This node launches none of these tasks,
does not repair historical hints/results and does not authorize further language,
navigation, AIR operation, Guard, MCP API or Skill feature development.
