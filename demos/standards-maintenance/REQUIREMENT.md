# SM-001: explicitly resolve URI-fragment JSON Pointers

Status: selected before implementation; **feature extension**, not a defect in
the previously documented JSON-string-only API. Baseline is
`77f37cefdee53e24651acabff2a990fbaa5d96c2` (component API 0.1.0).

## Source and scope

[RFC 6901 section 6](https://www.rfc-editor.org/rfc/rfc6901.html#section-6)
defines a UTF-8, percent-encoded URI-fragment representation. This has an
actual standardized use: [JSON Schema 2020-12 section 5](https://json-schema.org/draft/2020-12/json-schema-core#section-5)
assigns Pointer fragments to `application/schema+json`. This is a standards-based
adaptation, not a request from an ALVA customer. No remote schema retrieval,
schema validation, `$id` scope, `$anchor`, or full URI resolution is requested.
The caller already has the document and explicitly chooses the Pointer dialect.
In particular, `application/json` alone does not imply Pointer fragment semantics.

The bounded search is recorded in CANDIDATES.md. The historical issue
[json-schema-spec #328](https://github.com/json-schema-org/json-schema-spec/issues/328)
also demonstrates why the two representations must not be silently conflated.
No reference implementation or complete external fix was consulted.

## Observable contract

Add `json_patch.pointer.parse_fragment(string)` and
`json_patch.patch.resolve_fragment(json, string)`, plus explicit native request
mode `fragment` using the existing `pointer` field. Require a leading `#`;
decode exactly one percent-encoding layer to octets, validate strict UTF-8,
then apply existing JSON Pointer parsing and evaluation. `+` is literal, not
form-encoded space. Raw characters must satisfy RFC 3986 section 3.5 fragment
syntax. Percent-decoded `/` is a separator; `~1` remains the token escape for
a literal slash. No Unicode normalization. Empty fragment `#` is the root.

Reject malformed percent escapes, invalid UTF-8, raw forbidden URI characters,
non-Pointer anchors, full URLs, and invalid/missing Pointer targets. All
rejections require exit 1, classified stderr, empty stdout, and no panic.
Timeout, missing executable, signal/abnormal exit, and invalid/truncated JSON
are test failures, not successful rejections.

Existing `pointer` mode, `resolve`, `parse`, and Patch `path`/`from` remain
JSON-string-only; `%` remains literal there. Preserve exact JSON numbers,
release contracts/overflow, one request per process, 1 MiB adapter input limit,
caller timeout/status/result validation, owned mutators, and local dependencies.
Root removal remains unsupported. No AIR/AEP local-library editing is added.

## Allowed implementation layers

Fragment grammar, decoding order, and Pointer semantics belong in the ALVA
library. If necessary, add only a general checked octet-vector-to-UTF-8 string
primitive to stdlib/Rust glue (not a URI or Pointer implementation). No new
third-party package, decimal system, compiler redesign, or performance work.

## Acceptance fixed before implementation

`acceptance/cases.json` contains original tests authored by Codex this round
from RFC 6901 sections 3–7, RFC 3986 sections 2 and 3.5, and RFC 3629 section 4.
Literal expected outputs are not generated by ALVA or a copied decoder oracle.
They are not independent human-authored tests. Both versions use the same
entry point, exact/type-sensitive comparator, and real release executables.
All new positive cases must be rejected by the old adapter as unsupported and
pass on the new one. New invalid inputs must be specifically classified by
the new implementation. Adjacent old behaviors must match on both versions.

An application outside Core must consume the same library through
`alva.lib.toml`, check/build from another cwd, explicitly build release, wait for
each subprocess and validate results. No preparer or vendor source copy.
Existing upstream 108 enabled / 4 disabled tests and local boundaries remain
unchanged. Core, relevant stdlib/project, local dependencies, release safety,
exact caller path and native consumer regressions are also required.

Actual baseline output is captured by `reproduce.py --baseline-only` before
implementation and summarized in CHANGELOG.md / RESULTS.json; it is evidence
of documented lack of support, not a retroactive bug claim.
